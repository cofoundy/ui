# T-009 — core: `Timeline.keys` (Int32Array) truncates any realistic epoch `t0`, breaking `seek()`

role: core
blockedBy: []
scope.write: [src/components/chat-sim/core/**]
scope.read: [.cofoundy/specs/api-contract.md, .cofoundy/specs/file-ownership-matrix.md, .cofoundy/specs/architecture-v1.md, .cofoundy/context/agent-floor.md]

## Origen

Flagged by [capture] while building T-004's determinism test (`capture/__tests__/determinism.test.ts`).
Not fixed there — `core/**` is `core`'s exclusive `W` cell (file-ownership-matrix.md); `capture`
only has `R`. Worked around **inside `capture/**`** (see `capture/tickToStep.ts`'s header comment)
so T-004 isn't blocked on this landing, but the underlying bug is real and lives in `core/`.

## Repro (verified, not inferred)

```ts
const t0 = 1767261600000; // Date.UTC(2026, 0, 1, 9, 0, 0) — exactly what demo/index.html,
                           // chat-sim-element.ts's own attribute default, and every T-004 recipe use
console.log(t0 > 2147483647); // true — past Int32's ceiling (~24.8 days since epoch)
console.log(Array.from(Int32Array.from([t0, t0 + 1000]))); // [2030042203, 2030043203] — WRAPPED
```

`core/compile.ts`:

```ts
const keys = Int32Array.from(frames.map((f) => f.t));
```

`Timeline.keys` is typed `Int32Array` (`core/types.ts`) but populated straight from real epoch-ms
Ticks. Any script compiled with a realistic wall-clock `t0` (anything past ~1970-01-25) silently
wraps every entry via `ToInt32` — `keys[i]` stops equaling `frames[i].t`.

**This breaks `core/seek.ts`'s own exported `seek()`, not just a helper elsewhere could avoid**:
`upperBound()` binary-searches `keys` directly, comparing wrapped (~2e9) values against a raw,
unwrapped query `t` (~1.7e12 for a realistic date). The wrapped values are always numerically
smaller, so the search degenerates to "always at the end" — `seek(tl, t)` returns the FINAL state
for every `t`, regardless of which one is asked for, whenever `t0` is a realistic date.

Measured directly while building T-004: for the fixture at `capture/__tests__/fixtures/reserva.json`
compiled with `t0: 1767261600000`, querying `t` at the very first frame's tick returned
`tl.frames.length` (8) via the buggy path — i.e. "everything has happened" — instead of the correct
answer (0 or 1, depending on which side of that frame `t` falls).

## Por qué `core`'s own tests are green today

`core/__tests__/seek.test.ts` (and friends) evidently compile with small `t0` values (e.g. `0`),
which never crosses the Int32 boundary and hides this entirely. A `t0` matching any real calendar
date reproduces it every time.

## Acceptance (falsable)

1. `seek(tl, t)` returns the CORRECT state (not always the final one) for a `Timeline` compiled
   with `t0` set to a realistic epoch-ms date (e.g. `Date.UTC(2026, 0, 1, 9, 0, 0)`).
   **Gemelo negativo:** add this exact repro (or equivalent) as a regression test with a realistic
   `t0` — the existing small-`t0` tests must keep passing too; this is additive coverage, not a
   replacement for them (a suite that ONLY ever used realistic `t0` values going forward would hide
   a regression on the small-`t0` path just as easily as today's suite hides this one).
2. Fix candidates (either is acceptable, `core` picks): (a) change `Timeline.keys`'s type to a
   plain `number[]` / `Float64Array`, or (b) store keys relative to `t0` (`f.t - t0`, always small
   for any realistic script) and adjust `seek()`'s query accordingly. Whichever is chosen, the
   invariant `keys[i]` must let `upperBound` recover the SAME ordering as a direct compare on
   `frames[i].t` for every `i`, at any `t0` magnitude.
3. Once fixed, `capture/tickToStep.ts` (T-004) can be simplified back to searching `tl.keys`
   instead of `tl.frames` directly — flagged there as a follow-up, not blocking this task.
